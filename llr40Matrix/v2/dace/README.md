# DaCe's old and new CPU code generators on LLR-40

The question: does DaCe's new CPU code generator, which emits fewer connector copies than the old one,
give GCC code it vectorises where the old one does not, as Bonsall's semester project
(`References/DaCeCodegenAnalysis_AlexanderBonsall.pdf`) found on TSVC-2? And what do the DaCe columns cost
against the translated C column on the LLR-40 kernels?

## The dump: `codegen-20261006/`

Generated by Yakup Budanaz on 2026-10-06 at HPCAgent-Bench `5cfcb4f2` (`commit.txt`, branch
`release-v0.1`), which pins spcl/dace@`dea0b39c` (`extended`). For each of the 40 LLR-40 kernels it
holds three CPU renderings and three GPU (HIP) ones; only the CPU ones are used here.

| path | what |
|---|---|
| `<k>/cpu-canon/new_codegen/` | the `dace_cpu_canonicalize` column's code: the canonicalize pipeline, experimental_readable generator |
| `<k>/cpu-canon/old_codegen/` | the same SDFG through the classic configuration |
| `<k>/cpu-canon/cpf_cpp/` | DaCe's canonical parallel form, the self-contained C++ handed to agents |
| `db/cpf.json` | whether CPF rendered each kernel |

**These are optimised programs, not translations.** The pipeline is the fork's `canonicalize`
(directory `cpu-canon`, program `canon_cpu`), which restructures loops before code is generated: the
conditional minimum of `s316` becomes a `dace::reduce::min` library call, `s231` comes out interchanged
and split into thread bands, accumulators are privatised, and loops become OpenMP parallel loops. A DaCe
column is therefore closer to the agent column than to the translated C, C++ and Fortran columns.

**What "old" means.** Regenerating the dump shows that `old_codegen` is not the legacy generator alone
but the whole classic configuration that the `parallel`, `autoopt` and `loop2map` columns build with:

| setting | old (`CLASSIC_CODEGEN`) | new (`READABLE_CODEGEN`) |
|---|---|---|
| `compiler.cpu.implementation` | `legacy` | `experimental_readable` |
| `compiler.emit_tree_reductions` | off | on |
| `compiler.cpu.explicit_copy` | off | on |

With tree reductions off, a privatised sum is accumulated with one atomic update per element
(`dace::wcr_fixed<Sum>::reduce_atomic`) instead of an OpenMP `reduction(+:...)` clause; with explicit
copies off, single elements are moved with `dace::CopyND`. Both are visible in the dump: `s3111` and
`s319` use atomics only in `old_codegen`, and six kernels use `CopyND` only there. To separate these two
settings from the generator itself, this experiment adds a third configuration, `legacy`: the legacy
generator with tree reductions and explicit copies on.

## Cells

A cell is (kernel, pipeline, codegen), produced and timed by `dace_cells.py` through the harness at
`5cfcb4f2` (`dace.sbatch` runs it):

- pipeline `canon`: the canonicalize pipeline, as the column runs it; `none`: the parsed SDFG,
  simplified only, the setting of Bonsall's report ("without running the DaCe auto-vectorization
  pipeline");
- codegen `old`, `legacy`, `new` as above;
- kernels: the 40 LLR-40 kernels (`canon` only) and the four kernels of Bonsall's report, `s313`,
  `vdotr`, `s453`, `s314` (both pipelines);
- baselines at the same commit: translated C (`cc`, gcc 14) and translated C++ (`cpp`, g++ 13). DaCe's
  code is built by g++ 13 here (the harness pins the C++ family's compiler), so **C++ is the baseline
  the DaCe cells are compared with**. Against C, gcc 14's select-for-branch on `s316` and `s314` (the
  effect the thesis reports for `s316`) would show up as a 3.4x DaCe "speedup" that is the compiler.

Timing follows v2's protocol and geometry: preset M, `float64`, validation against the NumPy oracle, 5
warm-up and 30 timed calls, the fastest kept, one kernel per exclusive node, one core bound to NUMA
node 0, one OpenMP thread. Every column is timed by the harness's Python-side timer around the call
(DaCe's own instrumentation returns no native time at this commit). `vec_reports.py` compiles every
emitted cell (compile only) with g++ 13 and 14 under three flag sets: the column's own (`harness`),
Bonsall's (`bonsall`, with `-std=c++20` instead of `c++17`, which the runtime headers no longer
compile under), and Bonsall's plus `-funsafe-math-optimizations` (`unsafe`).

**Not comparable with v2's absolute times.** Between v2's commit (`26a4f0cf`) and `5cfcb4f2` preset M
was refit (`s311`: 220M -> 130M elements, `s275`: 12289 -> 9316, ...) and some kernels changed
(`wf_triangular`'s reference); translated C moved by 0.6x to 6.2x per kernel. All comparisons here are
within `5cfcb4f2`.

## Reproducing the dump

All 80 canon cells of the 40 LLR-40 kernels regenerate from `5cfcb4f2` + `dea0b39c`: 65 byte for byte,
15 with the same lines in a different order, and the only lines that move are declarations of local
temporaries (DaCe emits them in Python's randomised set order). `include/hash.h` differs in every
cell: it is a hash of the SDFG object, not of the code. Each emitted cell keeps the `dace.conf` it was
generated under (`emitted/<k>/<pipeline>_<codegen>/`).

## Results

All 232 timed cells validate against the NumPy oracle. Tables: `tables.md`; one row per cell with every
timing: `results.csv` (raw: `rows/`); loops vectorised per cell, compiler and flag set: `vec_summary.csv`
(GCC's reports, cut to the optimised lines and the not-vectorised reasons: `vec/reports/`).

**1. The new generator's fewer connectors change nothing.** `legacy` and `new` differ only in the
generator. They vectorise the same number of loops in every one of the 528 comparisons (44 kernels x 2
pipelines x 2 compilers x 3 flag sets), and on LLR-40 their times agree: geomean 1.00x, within 3% on 34
of 40 kernels. Of the other six, `s1232` and `s275` differ only in their fastest run (medians within
1%); `fuse_diamond`, `scatter_accum_dup` and `s152` are 3-4% slower with `new` and
`fuse_stencil_through_transient` is 8% faster. GCC copy-propagates the connector temporaries away.

**2. What the old configuration costs comes from two settings, not from the generator.**
- *Tree reductions off*: a privatised sum is accumulated with one atomic update per element. On one
  core this costs 12.4x on `s3111`, `s313` and `vdotr` and 6.0x on `s319`, and GCC vectorises nothing
  in those loops. These are the only reductions it affects; every other kernel is within 5% between
  `old` and `legacy` (`s1232`'s fastest run 11%, its medians equal), and the geomean over LLR-40, 1.12x,
  comes almost entirely from `s3111` and `s319`.
- *Explicit copies off*: a single element is moved with `dace::CopyND`, which GCC reports as a
  "complicated access pattern". It blocks vectorisation of `s311`, `s313`, `vdotr`,
  `quasi_affine_reduce_odd`, `s314` and `s316` without the pipeline, and of one loop of
  `versioned_distance_update` with it, and makes `s313`/`vdotr` without the pipeline 4.8x slower than
  C++.

**3. Bonsall's four kernels** (no pipeline, Bonsall's flags, g++ 13 and 14):

| kernel | report | here |
|---|---|---|
| `s313`, `vdotr` | GCC fails because the accumulator is written to memory every iteration | does not reproduce: with `legacy` or `new`, GCC vectorises the loop despite the store (the pointers are `__restrict__`, so it keeps the accumulator in a register and vectorises the sum in order, with no gain: same time as C++); only `old` fails, because of `CopyND` |
| `s453` | GCC needs `-funsafe-math-optimizations`, because of the copies around the induction variable | the flag is needed, but by all three configurations, `new` included, and by the hand-written C reference as well: the cause is the floating-point recurrence, not DaCe's copies |
| `s314` | needs both removing `dace::copy` and `-funsafe-math-optimizations` | reproduces exactly: `old` never vectorises (`CopyND`), `legacy`/`new` vectorise only with the flag |

The benchmark's hand-written C references (`<k>_reference.c`, gcc 13 and 14, Bonsall's flags) behave
exactly like `legacy`/`new`: `s313` and `vdotr` vectorise, `s453` and `s314` only with the flag, with
the same refusal ("unsupported use in stmt"). Bonsall's C++ ports, which the report says vectorise
`s453` and `s314` without it, are not part of this repository and were not tested.

**4. With the pipeline, the four patterns are gone.** `canon` privatises the dot products into an
OpenMP reduction, turns `s314` into a `dace::reduce::max` library call and replaces the induction
variable of `s453` by its closed form, which vectorises without any flag and runs 1.65x faster than
C++.

**5. The DaCe column against C++ (LLR-40, `canon`, `new`): geomean 1.42x.** The gains are the
pipeline's restructuring: interchange and distribution (`s2233` 11.7x, `s231` 10.5x, `s235` 9.6x,
`s2275` 9.4x, `s1232` 5.2x), fusion (`fuse_diamond` 5.6x, `fuse_stencil_through_transient` 2.4x), and
`s275` 2.3x and `s311` 1.8x. The losses: `compact_threshold_pack` 0.44x, `s323` 0.50x,
`scatter_accum_dup` 0.68x (an atomic scatter in every configuration), `s3112` 0.78x, and 0.94-0.95x on
`s115`, `wf_diff_skew` and `fuse_move_ifs`; 18 kernels are within 3%.

**6. Every one of these differences is explained by an experiment** that changes one thing, in DaCe's
generated code or in the translated C++: [followup/README.md](followup/README.md). Gains are restructurings
(also on `s119`, `s152`, `s233`, `s255`, `versioned_distance_update` and `wf_triangular`, which item 5 does not
list), losses are parallel forms on one thread.

## Layout

| path | what |
|---|---|
| `codegen-20261006/` | the dump, as received |
| `dace_cells.py` | one cell: `emit` (generate the program folder, compare with the dump) or `time` (harness `run_one`) |
| `vec_reports.py` | compile-only GCC vectorisation reports of every emitted cell |
| `dace.sbatch` | stages `emit`, `vec`, `time`, `retry` on daint |
| `analyze_dace.py` | `results.csv`, `vec_summary.csv`, `tables.md` |
| `emit.jsonl`, `emitted/` | every cell's generated code, SDFG and `dace.conf` |
| `rows/` | one JSON per timed cell: every timing, validation, node, settings |
| `vec/` | `vec_reports.csv` (with each compile's argv) and the cut-down reports |
| `logs/` | Slurm logs; `logs/cells/` the harness output of every timed cell |

Twenty cells of the first timing job failed before timing, because every cell recorded into one SQLite
DB of the harness (sharded by `SLURM_PROCID`, which is 0 in every step); they were re-run in job
4992662 with a DB per cell, and the C++ baseline in job 4992725. Jobs 4992521 and 4992598 generated with
an earlier definition of `old` and are superseded; 4992631 used the report flags with `-std=c++17`,
which does not compile.
