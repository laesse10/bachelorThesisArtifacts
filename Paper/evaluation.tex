\section{Experimental Setup}
\label{sec:setup}

\paragraph{Platform.}
All measurements ran on CSCS Alps \texttt{daint}. Each node has four NVIDIA GH200 chips with 72
Arm Neoverse V2 cores each. Every kernel ran alone on its own node and on a single core, so we
compare serial code, not parallel scaling.

\paragraph{Compilers.}
The benchmark compiles C with GCC 14.2, and C++ and Fortran with GCC 13.3; only GCC 14 supports
the C23 standard that the C flags request. All three get \texttt{-O3 -march=native}, a few
floating-point relaxations (no \texttt{errno}, no traps, no signed zeros), and
\texttt{-ffp-contract=fast}, which allows fused multiply-add (FMA) instructions.
\texttt{-ffast-math} is not used, because it changes results and would fail the comparison
with NumPy. Numba~0.67 compiles through LLVM, without \texttt{fastmath}.

\paragraph{Versions.}
We measure each kernel in six versions, which we call columns: the C, C++, Fortran and Numba
code generated from the NumPy reference; the hand-written C version, where it exists; and an
agent-optimised version. For the agent column, we take the best submission from the
benchmark's LLR-40 agent campaigns that still passes on our machine. These submissions come
from three open-weight models (Qwen3.8-27B, Kimi-K2.7 and GPT-OSS-120B). They were written and
graded on an AMD MI300A node as parallel OpenMP code; we run them unchanged on one thread.

\paragraph{Protocol.}
We fixed the measurement protocol before measuring. Each version is first checked against the
NumPy result at the measured size (preset M, \texttt{float64}). It then runs five times to warm
up and 30 times timed, and we keep every timing. A version that does not exist, or that gives a
wrong result, is recorded as such rather than dropped.

\paragraph{Statistics.}
About 14\% of all runs are slowed by roughly 1.6$\times$ by a temporary loss of memory
bandwidth. We ruled out the CPU clock, thread migration, huge pages and NUMA effects; the cause
lies outside our process. We therefore describe each cell by its fastest run, which the
slowdown rarely affects, and compute a speedup as the ratio of two such times. Following Hoefler
and Belli~\cite{hoefler2015benchmarking}, we summarise speedups by their geometric mean with a
95\% confidence interval.

\paragraph{Reproducibility.}
We measured the whole matrix twice, more than three weeks apart, with two versions of the
benchmark. All 240 cells have the same status in both, and 214 of the times agree within 5\%.
Most of the difference sits in five kernels (\texttt{s1232}, \texttt{s231}, \texttt{s235},
\texttt{s2275} and \texttt{s275}). They read their arrays with large strides, which makes them
very sensitive to memory bandwidth, and in most of their series hardly any run reached full
speed. For these kernels even the fastest run is unreliable, so we mark them in the figures and
do not compare their GCC versions. A second measurement, in which all versions of each of these
kernels took turns on the same node, confirmed this for four of them: the order of their GCC
versions changed from round to round, while the agent version was the fastest in every round.
For \texttt{s2275} the evidence is inconclusive. (Between the two benchmark versions, C++ also changed from
the C++23 to the C++20 standard, with no measurable effect.) We report the second measurement.

\section{Language Comparison}
\label{sec:language-comparison}

versions and one agent submission), and five give wrong results, all for the kernel

\paragraph{The language hardly matters.}
Compiled by the same compiler, the C, C++ and Fortran versions of a kernel run at almost the
same speed. On average, C++ is 1.04$\times$ and Fortran 0.98$\times$ as fast as C, and neither
difference is significant. The three are within 5\% of each other on 27 of the 39 kernels, and
five of the remaining twelve are the unreliable kernels. GCC's reports show why: it makes the
same vectorisation decisions for all three languages on 35 of the 39 kernels. No language wins
consistently.

\paragraph{Large gaps come from single decisions.}
Where the languages do differ, the cause is one detail of the generated code, not the language
itself. On \texttt{s3111}, Fortran is 5.8$\times$ slower than C. The translator writes each sum
as \texttt{sum = (sum + a(i))}, and Fortran compilers must respect such parentheses, so gfortran
cannot recognise the sum as a reduction. Allowed to ignore them (\texttt{-fno-protect-parens}),
gfortran splits the sum into vector partial sums, and the Fortran version becomes 1.7$\times$
\emph{faster} than C, because GCC does not reorder a sum in C without
\texttt{-fassociative-math}. On \texttt{s316}, the opposite happens: C is 3.4$\times$ slower than
C++ and Fortran, from identical code. Here the cause is the compiler version. GCC 14, used for C,
replaces a branch with a select instruction that makes every iteration wait for the previous one;
GCC 13 keeps the branch, which the processor predicts almost perfectly. Four smaller Fortran
losses of 4--6\% have a different cause, which we did not identify; the different compiler
versions are the obvious candidate.

\paragraph{The parentheses trade speed for exactness.}
The same parentheses also keep gfortran from fusing a multiplication and an addition into one
FMA instruction. This makes Fortran 1.25$\times$ slower on \texttt{scan\_affine\_decay} and
1.1$\times$ slower on \texttt{versioned\_distance\_update}, where the value carried between
iterations enters the multiplication, but 3\% faster on \texttt{s323}, where it only enters
additions. Without the parentheses, gfortran uses FMA like C: it catches up with C on the first
two kernels and loses its lead on \texttt{s323}. In exchange, the parentheses
make Fortran exact: on eight affected kernels, the default Fortran results are bit for bit
identical to NumPy's. C and C++ match NumPy on the sums but not where they use FMA; there,
between a third and almost all of the elements differ, by at most 5 units in the last place on two kernels but by up to
$4.5\cdot10^{-7}$ relative on the recurrence \texttt{s323}, where the error accumulates. Once its
parentheses may be ignored, Fortran produces exactly C's results on the FMA kernels, and its
reordered sums differ from NumPy by about $2\cdot10^{-13}$ relative. All of these versions pass the benchmark's tolerance.

\paragraph{Numba behaves like its compiler, LLVM.}
Numba is the most uneven column: faster than C on 8 kernels, slower on 16, and 0.88$\times$ as
fast overall. It is 2.4$\times$ faster on \texttt{s2710}, a loop full of branches that LLVM
vectorises and GCC does not. GCC fails on a single line: a test of \texttt{x[0]}, a scalar that
the translator passes as a one-element array and reads inside the loop. Moving that read in
front of the loop, a one-line change, lets GCC vectorise the loop too; the C version then runs
2.7$\times$ faster and slightly ahead of Numba. Numba is 2.5 to 3.6$\times$ slower on four
reductions with a conditional update, where LLVM makes the same choice as GCC 14 on
\texttt{s316}: a select instead of a branch. This choice between branch and select is the most
common cause of large gaps in the matrix, in both directions, and it depends on how strictly NaNs
must be handled. Allowed to ignore them (\texttt{-ffinite-math-only}), GCC vectorises the plain
minimum \texttt{s316}, which then runs 4.0$\times$ faster in C, but turns the three reductions that
also track an index into selects and makes them 3.4 to 3.7$\times$ slower.

\paragraph{Values passed through memory cost time.}
A second recurring cause is whether a value carried from one iteration to the next stays in a
register or goes through memory. In \texttt{versioned\_distance\_update}, the translated C version
stores a value and reads it back in the next iteration and needs 10.1 cycles per element; the
agent version keeps the value in a register and needs 4.2, which makes it 2.4$\times$ faster. In
\texttt{wf\_triangular}, the same happens between GCC (2.2 cycles, register) and Numba (8.1
cycles, memory). Changing only how the value is carried removes the difference in both kernels.
Measured with hardware counters, the detour through memory costs 6.1 and 6.0 cycles per element.

\paragraph{Compilers do not restructure loops; the agents do.}
In the interchange and distribution kernels, GCC never interchanges or splits a loop. It sees
that the inner loops access memory with large strides and decides that vectorising them is not
worth it. The agents restructured these loops by hand, after which GCC could vectorise them.
This makes the agent versions 3 to 10$\times$ faster than any other version, and they stay fast
in every run, even on the unreliable kernels. The hand-written C column shows the same effect:
it is 5.6$\times$ faster than translated C on \texttt{fuse\_diamond} and 2.3$\times$ faster on
\texttt{fuse\_stencil\_through\_transient}, because the hand-written versions are already fused,
while the NumPy versions are deliberately not. On these kernels, the hand-written version is the
optimised answer rather than a baseline.

\paragraph{Agent code is tied to the machine it was written for.}
Agent code is the fastest column overall (1.54$\times$ as fast as C), but it is slower than C on
eight kernels. In the cases we inspected, the reason is code designed for many threads. The scan
in \texttt{scan\_affine\_decay} reads its input twice to allow parallelism, and is 2.0$\times$
slower on one thread. The version of \texttt{scatter\_accum\_dup} assumes the 48-thread MI300A
node it was written for, overrides our single-thread setting, and is 2.7$\times$ slower. For 12
kernels, the best agent submission did not even compile here, because it used x86-only
instructions. A speedup on one machine does not automatically carry over to another.

\paragraph{Vectorising is not the same as being fast.}
GCC vectorises at least one loop in 15 of the 39 kernels in C and in 12 in Fortran; in the
agents' code, it vectorises loops in 27 kernels. On this processor, a vector holds only two
\texttt{float64} values, so vectorising alone can gain at most about 2$\times$. Restructuring can
gain far more, because it changes how the loops access memory. Vectorising also does not
guarantee a gain: on the sum \texttt{s311}, the vectorised C version is exactly as fast as the
scalar Fortran version (135\,ms), because the additions still happen one after the other. Only
the agent version, which reorders the additions, is faster (76\,ms). Bonsall and
Budanaz~\cite{bonsall2026dace} found the same for code generated by DaCe.

\paragraph{Fused multiply-add can decide correctness.}
\label{par:fma}
The kernel \texttt{s115} produces numbers so large that, at the measured size, its output is
almost entirely infinity or NaN. With FMA, the GCC versions round slightly differently from
NumPy, the overflow happens in a different place, and all four fail the check. With FMA turned
off, all four pass. Numba passes in both cases, because it reproduces NumPy's arithmetic
exactly. The two wavefront kernels overflow as well, but they only add numbers, so every version
produces the same output and passes without really being tested. At smaller sizes, where all
outputs stay finite, every version passes and the timings show the same pattern.
